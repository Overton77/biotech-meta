### 2. The uid to id seam

Decision from the coordinator: catalog identity is `uid` (`hu:<type>:<opaque-stable-id>`), the live `id: ID! @id` is the projection identity, and nobody renames the live field. Proposal for the seam:

1. **Both are stored.** `uid` is an additional stored property on every catalog-participating node. It is exposed to GraphQL as an additive nullable field `uid: String` with no `@id`, so the library never generates or overwrites it. It becomes `String!` after backfill.
2. **Derivation.** `id` equals the opaque segment of `uid` (the text after the second colon). For nodes created through the GraphQL API, `uid = 'hu:' + token(label) + ':' + id`. For nodes created by ingestion, the writer generates an opaque, globally unique segment (UUID or ULID), sets `uid`, and sets `id` to the segment. No lookup table is needed in either direction, and the catalog's global uid uniqueness (V-000a) holds if the segment is globally unique.
3. **Type token.** The `<type>` segment comes from a registry, `conventions.uidTypeTokens` in `../catalog/schema.yaml` (0.2.0; merged from the lane's catalog-patch fragment). It is not computed from the label. The existing fixtures use tokens such as `org`, `product`, `material`, `snapshot`.
4. **Stored id property.** The `id` is stored under `id` except for `Document` (`documentId`), `DocumentTextVersion` (`documentTextVersionId`), `Segmentation` (`segmentationId`) and `Chunk` (`chunkId`). Cypher and the validator use `coalesce(n.id, n.documentId, n.documentTextVersionId, n.segmentationId, n.chunkId)`. V-117 checks the rule.
5. **Immutability and merges.** Neither `uid` nor `id` changes. If two nodes are found to be one, the survivor keeps its uid and the other's uid stays resolvable as a tombstone with a recorded equivalence (an `EquivalenceAssessment`). Old answers that cite the tombstone uid remain interpretable.
6. **Opaque in production.** The fixtures use readable segments (`hu:product:elysium-basis`). That is illustrative. Production segments must carry no name, because a segment that reads as a name invites identity by name. The seam adds no constraint that can detect this; it is an ingestion rule.
7. **Uniqueness.** `uid` unique constraints are created per live label (C-101), since the live labels carry no archetype label. The catalog's archetype-label constraints in `neo4j/constraints.cypher` apply once archetype labels are added (see the `Entity` row).

Failing case this prevents: an ingestion service writes a node by Cypher with a `uid` and no `id`. The GraphQL layer then returns an error for the non-null `id`, or a Cypher `MERGE` on `id` creates a duplicate of the same entity under a second identity.

### 5. Label seam for catalog archetypes

The catalog's archetype labels (`:Entity`, `:VersionedState`, `:Occurrence`, `:InformationArtifact`, `:Assertion`, `:EvidenceAssessment`) are Neo4j labels. The live `Entity` is a GraphQL interface. Two ways to reconcile:

- **Add labels.** Use `@node(labels: [...])` to carry the archetype labels, and backfill existing nodes (`MATCH (n:Product) SET n:Entity`). The catalog's own constraints then apply unchanged. Whether the library's generated queries stay correct with extra labels is unverified here.
- **Per-label constraints.** Keep live labels as they are and create per-label `uid` constraints (C-101). Cross-label uniqueness is then checked by V-000a over a label list.

Recommendation: per-label constraints first (no change to generated queries), then add archetype labels when a round needs archetype-level validation over live nodes. Until then, treat `V-000a` and `V-000b` as vacuous for live-created nodes.

### Migration notes

1. Backfill `SourceSnapshot` for each `DocumentTextVersion` from stored capture metadata; where none exists, create a snapshot with `captureCompleteness: UNKNOWN` and `contentHash` over the stored text (`contentHashBasis: NORMALIZED_TEXT`).
2. For each `SUPPORTED_BY` edge to a Chunk with `ExtractionMetadata.quoteSpan`, create a TEXT_QUOTE locator (exact = quoteSpan; else the chunk text, flagged) on the chunk's text version snapshot, and set `locatorUid` on the edge.
3. Add the `Assertion` label to each `ClaimOccurrence`; copy `UTTERED_BY` to `ASSERTED_BY`; split occurrences with several speakers into one per speaker.
4. Move `Claim.evidenceStrength` into `ClaimEvidenceAssessment` (PROPOSED, `legacy-unspecified`).
5. Split multi-subject `RelationshipAssertion`s; convert cross-claim ones into `ClaimEvidenceAssessment`.
6. Create one `Activity` per distinct `mongoResearchRunId`; link outputs with `WAS_GENERATED_BY`. Record that only the last writer is known for legacy nodes.
7. Re-type `Person-[:RECOMMENDS]->` edges: keep only those whose originating occurrence is a recommendation; others become occurrences with `speechAct` REPORTS_PRACTICE or STATES.
